## 1. Technical overview

| Section | Content |
|---------|---------|
| Description | Hijack Execution Flow: DLL (T1574.001) Adversaries abuse dynamic-link libraries (DLLs) to gain persistence, escalate privileges, and evade defenses. Because DLLs contain code and data shared across programs, they can be manipulated so that a legitimate, trusted process loads attacker-controlled code instead of (or alongside) the intended library. This lets adversaries operate under the cover of a benign, potentially elevated process, often with payloads that are encrypted, packed, or obfuscated until loaded into memory.<br/><br/>Common variants include:<br/>- **DLL Side-Loading** – Placing a malicious DLL next to a legitimate (and signed) application, then invoking that app so it loads the attacker's payload. Loaders can be chained or split across multiple DLLs to fragment functionality and frustrate analysis.<br/>- **DLL Search Order Hijacking** – Planting a malicious DLL in a directory that Windows checks earlier in its search sequence than the legitimate library's location.<br/>- **DLL Redirection** – Modifying the search order via the Registry or a redirection/manifest file so a program loads a DLL from a different location.<br/>- **Phantom DLL Hijacking** – Supplying a DLL for a reference to a non-existent module, using the expected name and path.<br/>- **DLL Substitution** – Replacing a valid DLL with a malicious one of the same name and location. |
| **Attack Variant in Evidence** | This case demonstrates **Atomic Test #6** from Atomic Red Team's T1574.001 implementation using KeyScrambler application:  <br/>1. Legitimate KeyScrambler application searches for `KeyScramblerIE.dll`  <br/>2. When executed from `%TEMP%`, it searches the temp directory first  <br/>3. Attacker places malicious `KeyScramblerIE.dll` in `%TEMP%`  <br/>4. The malicious DLL loads with the privileges of KeyScrambler.exe  |
| Execution model | **Three variants were observed in this investigation:**<br><br>**1. System DLL cloning and staging**<br>A legitimate system DLL is copied, renamed to the target name (`WinAppXRT.dll` or `ualapi.dll`), and placed in both `%USERPROFILE%\AppData\Roaming\` and `%windir%\System32\`. An environment variable (`APPX_PROCESS`) or a service configuration (`sc config Spooler start=auto`) is then manipulated to redirect DLL loading to the hijacked path.<br><br>**2. Third-party application DLL hijack (KeyScrambler)**<br>A legitimate signed application is installed. Its kernel driver (`keyscrambler.sys`) and supporting DLLs are registered in paths that participate in the DLL search order, providing a persistent hijacking vehicle through trusted-software DLL loading.<br><br>**3. Executable staging (`updater.exe`)**<br>A binary renamed to `updater.exe` is placed in `%USERPROFILE%\AppData\Roaming\`. Applications that call `CreateProcess("updater.exe")` without a fully qualified path resolve to the user-controlled copy before searching System32. |
| Tactics & Techniques | TA0003 – Persistence<br>• T1574.001 – Hijack Execution Flow: DLL Search Order Hijacking<br><br>TA0004 – Privilege Escalation<br>• T1574.001 – (when elevated context loads the rogue DLL)<br><br>TA0005 – Defense Evasion<br>• T1574.001 – Execution within trusted process context |
| Privileges | User-level for user-path staging; administrative privileges required to write to `%windir%\System32\`. |
| OS | Windows (observed: Windows 10, build 19041.4355) |
| Network | Not applicable. No network-based C2 was observed. |

## 3. Non-volatile artifacts

Persistent data written to disk or registry during technique execution.

### 3.1 Rogue DLL placement – WinAppXRT.dll hijack

**Source:** $MFT

Two copies of `WinAppXRT.dll` were placed on disk within one second of each other:

```
MFT Entry 125442 | %USERPROFILE%\AppData\Roaming\WinAppXRT.dll
  $STDINFO Created:      2026-06-04 07:25:08 UTC
  $STDINFO Modified:     2024-08-16 12:47:33 UTC  (source binary timestamp preserved by copy)
  $FILENAME Created:     2026-06-04 07:25:08 UTC

MFT Entry 125447 | %windir%\System32\WinAppXRT.dll
  $STDINFO Created:      2026-06-04 07:25:09 UTC
  $STDINFO Modified:     2024-08-16 12:47:33 UTC  (identical to AppData copy)
  $FILENAME Created:     2026-06-04 07:25:09 UTC
```

The staging command captured in process creation events:

```
cmd.exe /c copy %windir%\System32\amsi.dll %APPDATA%\amsi.dll
        & ren %APPDATA%\amsi.dll WinAppXRT.dll
        & copy %APPDATA%\WinAppXRT.dll %windir%\System32\WinAppXRT.dll
        & reg add "HKEY_CURRENT_USER\Environment" /v APPX_PROCESS /t REG_EXPAND_SZ /d "1" /f
```

`WinAppXRT.dll` is not a known baseline Windows DLL. When a file is copied using the `copy` command, the target inherits the source's modification time while receiving a new creation time — making the timestamp mismatch between `$STDINFO Modified` and `$STDINFO Created` a reliable indicator of a placed file.

#### What to look for?

- DLLs in System32 with creation dates postdating OS installation
- DLLs in `%USERPROFILE%\AppData\Roaming\` with names matching Windows system DLLs
- `$STDINFO Modified` significantly older than `$STDINFO Created` on the same file

### 3.2 Rogue DLL placement – ualapi.dll hijack

**Source:** $MFT

```
MFT Entry 125477 | %USERPROFILE%\AppData\Roaming\ualapi.dll
  $STDINFO Created:      2026-06-04 07:25:08 UTC
  $STDINFO Modified:     2024-08-16 12:47:33 UTC
  $FILENAME Created:     2026-06-04 07:25:08 UTC

MFT Entry 125495 | %windir%\System32\ualapi.dll
  $STDINFO Created:      2026-06-04 07:25:09 UTC
  $STDINFO Modified:     2024-08-16 12:47:33 UTC
  $FILENAME Created:     2026-06-04 07:25:09 UTC
```

Staging command:

```
cmd.exe /c copy %windir%\System32\amsi.dll %APPDATA%\amsi.dll
        & ren %APPDATA%\amsi.dll ualapi.dll
        & copy %APPDATA%\ualapi.dll %windir%\System32\ualapi.dll
        & sc config Spooler start=auto
```

`ualapi.dll` (User-mode Application Licensing API) is loaded by `spoolsv.exe` (Print Spooler, SYSTEM). Placing a rogue copy in System32 and enabling automatic Spooler start ensures the malicious DLL is loaded at every boot by a SYSTEM-privileged service. The same `$STDINFO Modified` anomaly described in section 3.1 applies.

#### What to look for?

- `ualapi.dll` in System32 with creation date after OS installation
- `$STDINFO Modified` significantly older than `$STDINFO Created`
- `sc.exe` command line setting Spooler start type to automatic, correlated with DLL placement in the $MFT

### 3.3 Executable staging – updater.exe

**Source:** $MFT

```
MFT Entry 125430 | %USERPROFILE%\AppData\Roaming\updater.exe
  $STDINFO Created:      2026-06-04 07:25:08 UTC
  $STDINFO Modified:     2024-08-16 12:49:46 UTC
  $FILENAME Created:     2026-06-04 07:25:08 UTC
```

The staging command (captured in process creation events) copied `powershell.exe` and renamed it:

```
cmd.exe /c
  copy %windir%\System32\windowspowershell\v1.0\powershell.exe %APPDATA%\updater.exe
  & copy %windir%\System32\amsi.dll %APPDATA%\amsi.dll
  & %APPDATA%\updater.exe -Command exit
```

System Monitor confirmed that `updater.exe` subsequently loaded `amsi.dll` from the same AppData directory:

```
updater.exe (PID 4084) – Load Image
  Path: %USERPROFILE%\AppData\Roaming\amsi.dll
  Base: 0x7fffd56a0000, Size: 0x1f000
```

This is the most direct confirmation of DLL hijacking in the evidence: a DLL was loaded from a user-writable path rather than from System32.

#### What to look for?

- Executables in `%USERPROFILE%\AppData\Roaming\` with names typical of update helpers (`updater.exe`, `helper.exe`)
- `$STDINFO Modified` significantly older than `$STDINFO Created` — renamed copy of a system binary
- Load Image events showing `.dll` files loaded from `%USERPROFILE%\AppData\Roaming\`

### 3.4 KeyScrambler – third-party DLL hijacking scenario

**Source:** $MFT, Amcache

```
MFT Entry 125496 | %USERPROFILE%\AppData\Local\Temp\KeyScrambler_Setup.exe
  $STDINFO Created:  2026-06-04 07:25:11 UTC

MFT Entry 125528 | %USERPROFILE%\AppData\Local\Temp\KeyScrambler.exe
  $STDINFO Created:  2026-06-04 07:25:20 UTC
  $STDINFO Modified: 2025-12-06 20:36:42 UTC

Installation: %ProgramFiles(x86)%\KeyScrambler\  (DLLs and kernel driver)
```

Amcache recorded execution with SHA1 hashes:
- `KeyScrambler_Setup.exe` SHA1: `b54192227862c0c87470186b0f1d5493aa2bf5f5` (version 3.19.0.0)
- `KeyScrambler.exe` SHA1: `eb8add063c5e846f6211c321d42cf2aaed3cfe1b` (version 3.19.0.0)

This scenario demonstrates that legitimate signed applications can be exploited as DLL hijacking vehicles. If a trusted application loads DLLs from a user-writable path, an attacker can substitute a rogue DLL with the same name to achieve code execution under that application's context. Amcache entries confirm execution and provide hashes for cross-system attribution.

#### What to look for?

- Installer binaries in `%USERPROFILE%\AppData\Local\Temp\` with creation timestamps correlated with DLL placement activity
- Amcache entries for newly installed applications that load DLLs from non-standard paths
- EID 7045 driver registration events concurrent with file placement activity in the $MFT

### 3.5 Registry modification – HKCU\Environment

**Source:** Registry (NTUSER.DAT)

The following values were observed under `HKEY_CURRENT_USER\Environment`:

| Value | Type | Data |
|-------|------|------|
| APPX_PROCESS | REG_EXPAND_SZ | 1 |
| TEMP | REG_EXPAND_SZ | %USERPROFILE%\AppData\Local\Temp |
| TMP | REG_EXPAND_SZ | %USERPROFILE%\AppData\Local\Temp |

`APPX_PROCESS` was written by `reg.exe` during the DLL staging phase. After being set, `svchost.exe` (AppXSvc) enumerated `HKCU\Environment` and read the value, confirming propagation to a system component.

`TEMP` and `TMP` define the directory used for temporary file operations. If an attacker redirects these values to an attacker-controlled path, applications that load DLLs from the temp directory will load from the substituted location. `APPX_PROCESS` similarly influences how AppX (MSIX) packaged processes resolve DLL paths.

Environment variables under `HKCU\Environment` propagate to all new user processes and persist across logons. Unlike writing to System32, modifying `HKCU\Environment` is a user-level operation — no elevation required.

#### What to look for?

- `HKCU\Environment\APPX_PROCESS` present with any non-empty value
- `HKCU\Environment\TEMP` or `TMP` pointing to non-standard paths
- Registry writes to `HKCU\Environment` correlated in time with DLL placement events in the $MFT

### 3.6 Service installation – EID 7045

**Source:** Windows Event Logs (System)

Event ID 7045 ("A new service was installed in the system") is generated by the Service Control Manager whenever a service or kernel driver is registered. It is written to the Windows System event log and requires no additional instrumentation.

EID 7045 fields:

| Field | Description |
|-------|-------------|
| ServiceName | Registered name of the service |
| ImagePath | Binary or driver path (may be relative, e.g., `System32\drivers\<name>.sys`) |
| ServiceType | Kernel driver, user-mode service, etc. |
| StartType | Automatic, manual, disabled, boot, system |
| AccountName | Account under which the service runs |

In this investigation, EID 7045 recorded the KeyScrambler kernel driver installation:

| Timestamp (UTC+2) | ServiceName | ImagePath | StartType |
|-------------------|-------------|-----------|-----------|
| 2026-06-04 08:44:36 | KeyScrambler | `System32\drivers\keyscrambler.sys` | On-demand |
| 2026-06-04 09:25:18 | KeyScrambler | `System32\drivers\keyscrambler.sys` | On-demand |

In a DLL hijacking scenario where an attacker installs a service to load a rogue DLL at boot, EID 7045 provides primary detection. Unlike process creation events (which require audit policy configuration), EID 7045 is written by the kernel and cannot be suppressed by user-mode processes.

#### What to look for?

- `ImagePath` referencing `System32\drivers\<name>.sys` where the driver is not in the system baseline
- EID 7045 timestamps correlated with DLL creation events in the $MFT
- `StartType: Automatic` or `StartType: Boot` — driver loads at every boot
- Service installation by a user account rather than `SYSTEM`

### 3.7 Prefetch FilesLoaded entries and BAM execution records

**Source:** Prefetch files, Registry (BAM)

#### Prefetch FilesLoaded

Prefetch files record the full volume-relative paths of DLLs loaded during an executable's runs. These paths persist in the Prefetch file even after the originating files are deleted.

Prefetch entries for the KeyScrambler installer recorded the following DLL loads from a temporary NSIS extraction directory:

```
\VOLUME{01daef485d34f57f-445d45b9}\USERS\DUMMY\APPDATA\LOCAL\TEMP\NSNEA43.TMP\USERINFO.DLL
\VOLUME{01daef485d34f57f-445d45b9}\USERS\DUMMY\APPDATA\LOCAL\TEMP\NSNEA43.TMP\SYSTEM.DLL
\VOLUME{01daef485d34f57f-445d45b9}\USERS\DUMMY\APPDATA\LOCAL\TEMP\NSNEA43.TMP\NSEXEC.DLL
```

NSIS-based installers extract plugins to a randomly named temporary folder and load them via `LoadLibrary`. An attacker who can write to the Temp directory before the installer runs can substitute a rogue DLL with the same name as an expected plugin. The Prefetch FilesLoaded entries confirm this load path and persist forensically even after the Temp directory is cleaned up.

#### What to look for?

- FilesLoaded paths pointing to `%USERPROFILE%\AppData\Local\Temp\<random_subdir>\`
- System-sounding DLL names (`System.dll`, `UserInfo.dll`) appearing under Temp subdirectories
- Any executable whose Prefetch FilesLoaded entries show DLL loads from `AppData`, `Temp`, or `Downloads`

#### BAM execution records

The Background Activity Moderator (BAM) registry key records the last execution time of user-mode executables under `HKLM\SYSTEM\ControlSet001\Services\bam\State\UserSettings\<SID>\`.

`reg.exe` was recorded with a last execution timestamp of **2026-06-04 07:25:09 UTC** — the same second as DLL placement in the $MFT. This corroborates the `HKCU\Environment\APPX_PROCESS` registry write and confirms a registry utility was invoked during the staging phase.

#### What to look for?

- `reg.exe` BAM timestamps correlated with DLL placement timestamps in the $MFT
- Registry tool executions (`reg.exe`, `regedit.exe`) within the same time window as file creation events in user-writable paths

## 4. Volatile artifacts

Evidence produced during technique execution: process creation events and DLL load operations observed at runtime.

### 4.1 Process execution chain

**Source:** Windows Event Logs (Sysmon EID 1 / Security EID 4688), System Monitor

System Monitor captured the complete process creation and DLL load sequence.

**Phase 1 – updater.exe staging and DLL load:**

```
9:25:08.666 AM | powershell.exe (PID 4060) → cmd.exe (PID 3652) [Process Create]
  Command: cmd.exe /c
    copy %windir%\System32\windowspowershell\v1.0\powershell.exe %APPDATA%\updater.exe
    & copy %windir%\System32\amsi.dll %APPDATA%\amsi.dll
    & %APPDATA%\updater.exe -Command exit

9:25:08.721 AM | cmd.exe (PID 3652) → updater.exe (PID 4084) [Process Create]

9:25:08.857 AM | updater.exe (PID 4084) – Load Image [DLL HIJACK CONFIRMED]
  Path: %USERPROFILE%\AppData\Roaming\amsi.dll
  Base: 0x7fffd56a0000, Size: 0x1f000
```

**Phase 2 – WinAppXRT.dll staging:**

```
9:25:09.464 AM | powershell.exe (PID 4060) → cmd.exe (PID 4560) [Process Create]

9:25:09.506 AM | cmd.exe (PID 4560) – SetRenameInformationFile
  Source: %USERPROFILE%\AppData\Roaming\amsi.dll
  Target: %USERPROFILE%\AppData\Roaming\WinAppXRT.dll

9:25:09.507 AM | cmd.exe (PID 4560) – CreateFile (write)
  Path: %windir%\System32\WinAppXRT.dll

9:25:09.523 AM | reg.exe (PID 2260) – RegSetValue
  Key: HKCU\Environment\APPX_PROCESS = 1 (REG_EXPAND_SZ)
```

The Load Image event at 9:25:08.857 AM provides the most direct evidence of successful hijacking: `amsi.dll` was loaded from `%USERPROFILE%\AppData\Roaming\` rather than `%windir%\System32\`.

#### What to look for?

- `cmd.exe` or `powershell.exe` spawning file copy and rename operations targeting DLL names
- Load Image events for `.dll` files with paths under `%USERPROFILE%\AppData\`
- Parent-child chains: shell process → file operations in AppData → execution from AppData
