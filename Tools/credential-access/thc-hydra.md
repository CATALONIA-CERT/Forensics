    ## 3. Non-volatile artifacts

    The proof of concept was executed in a controlled environment.

    **Scope:**

    - Linux systems inside a controlled network environment
    - Requests against an ad hoc login form
    - Analysis of Apache `access.log`
    - Collection of forensic evidence
    - Subsequent forensic analysis

    **What was not done:**

    - No exploits or advanced evasion techniques were used
    - No real credentials were used
    - No malicious binaries were executed on the target or victim system

    In this scenario, Hydra does not execute code on the target system. The most relevant forensic evidence is derived from **server-side logs**, mainly web server, WAF, proxy and authentication logs.

    As a result:

    - No malware is deployed on the target system
    - No persistence mechanism is created
    - No binary execution is expected on the victim system
    - No host-based artifact directly related to Hydra execution is expected on the victim
    - The key evidence is found in HTTP request logs and authentication telemetry

    ## 4. Volatile artifacts

    Evidence generated during HTTP/HTTPS interaction, including authentication attempts, runtime web activity and network behavior.

    ### 4.1 OS Interaction artifacts

    On the target system, there is no direct execution of THC-Hydra. The interaction occurs through HTTP/HTTPS requests against the exposed authentication service.

    Relevant observations:

    - No interactive session is created on the target system
    - No direct process execution by Hydra occurs on the victim
    - The web server processes the requests as regular HTTP traffic
    - The login application receives repeated authentication attempts
    - If valid credentials are found, subsequent successful access events may appear after the brute-force phase

    ## 5. User-Agent manipulation and IOC limitations

    In HTTP/HTTPS modules, THC-Hydra may generate an identifiable `User-Agent` header. In the laboratory test, the following value was observed:

    ```text
    Mozilla/5.0 (Hydra)
    ```

    This indicator is useful during the initial triage phase because it allows analysts to quickly identify activity compatible with Hydra in web logs, proxy logs, WAF logs or network captures.

    However, from a forensic perspective, this should be treated as a relevant but easily manipulated IOC.

    The `User-Agent` header is controlled by the client. This means that the entity sending the request can modify it or replace it with another value.

    In other words, literal `User-Agent` detection is useful but fragile. It is especially effective against default executions, internal laboratories, authorized tests or low-sophistication actors. However, it is not sufficient against operators who modify headers or use intermediary infrastructure.

    Therefore, detection should not rely exclusively on static strings. It should be complemented with behavioral analysis, including:

    - Volume of authentication attempts
    - Repetition against authentication endpoints
    - Source IP behavior
    - HTTP methods used
    - HTTP response codes
    - Time-based request patterns
    - Possible successful logins after multiple failed attempts
    - Correlation with WAF, proxy, SIEM or authentication logs

    ## 6. Detection rules and collection targets

    ### Recommended collection targets

    | Source | Collection target |
    |------|-------------------|
    | Web server | `access.log`, `error.log` |
    | WAF | HTTP request logs, blocked requests, suspicious automation events |
    | Reverse proxy | Source IP, URI, method, status code and headers |
    | SIEM | Aggregated authentication attempts and web events |
    | Network | PCAP or NDR telemetry |
    | Application | Login success and failure logs |

    ### Detection logic

    Detection should combine static and behavioral indicators.

    **Useful static indicators:**

    - `User-Agent` equals `Mozilla/5.0 (Hydra)`
    - `User-Agent` contains `Hydra`

    **Useful behavioral indicators:**

    - Multiple login attempts from the same source IP
    - High number of POST requests to `/login.php` or other authentication endpoints
    - Repeated failed authentication attempts
    - Password spraying pattern against multiple users
    - Credential stuffing pattern using multiple credential pairs
    - Successful login after a high number of failed attempts

    logsource:

      selection_exact:

    ## 7. Recommendations

    The observed `User-Agent` value `Mozilla/5.0 (Hydra)` is a strong indicator in the laboratory context and allows high-confidence attribution of the observed HTTP activity to THC-Hydra under the tested configuration.

    However, in real environments, this IOC should not be used in isolation because the `User-Agent` is controlled by the client and can be modified.

    Recommended actions:

    - Use `User-Agent` detection as an initial triage mechanism
    - Correlate the IOC with authentication behavior
    - Monitor repeated POST requests against login endpoints
    - Review failed and successful authentication attempts
    - Correlate source IPs with request volume and response codes
    - Include WAF, proxy, web server and application logs in the investigation
    - Prioritize behavior-based detections over static string matching
    - Treat successful logins after repeated failures as high-priority events
    - Document whether the activity belongs to authorized testing, internal laboratories or unauthorized access attempts

    ## 8. Conclusion

    During the test, the `User-Agent` value `Mozilla/5.0 (Hydra)` was identified in the Apache `access.log` file, associated with multiple HTTP requests against the `/login.php` endpoint.

    This indicator allows the observed activity to be attributed with high confidence to THC-Hydra in the laboratory configuration.

    However, the `User-Agent` is a client-controlled header and can be modified. For this reason, detection based exclusively on this IOC is insufficient in real environments.

    Detection should be complemented with behavioral analysis, especially:

    - Number of authentication attempts
    - Repetition against authentication endpoints
    - Source IP activity
    - HTTP response codes
    - Possible successful access after failed attempts
